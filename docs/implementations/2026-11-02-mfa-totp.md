# MFA TOTP

Fecha: 2026-11-02
Issue: #52 — Añadir MFA TOTP

## Contexto

Las cuentas solo se protegían con contraseña. Se añade un segundo factor TOTP
compatible con apps autenticadoras, un desafío en el login y códigos de recuperación de
un solo uso.

## Decisión

- TOTP implementado con `node:crypto` (HMAC-SHA1, 6 dígitos, periodo 30 s, ventana ±1)
  y un codec Base32 propio, sin nuevas dependencias. Verificado con los vectores de la
  RFC 6238.
- Alta en dos pasos:
  - `POST /auth/mfa/enroll` (autenticado) exige la contraseña actual, genera un secreto
    de 20 bytes y devuelve `{ secret, otpauthUrl }`. Es idempotente mientras el alta
    está pendiente.
  - `POST /auth/mfa/activate` confirma un TOTP válido, activa MFA, devuelve 10 códigos
    de recuperación en claro (solo se guardan sus hashes SHA-256) y revoca las sesiones
    de refresh existentes.
- Login con MFA activo:
  - `POST /auth/login` valida credenciales y aplicación y responde
    `{ mfaRequired: true, challengeToken, expiresIn }` sin tokens.
  - El challenge es un JWT de tipo `mfa` (300 s por defecto,
    `MFA_CHALLENGE_EXPIRATION`) con usuario, rol, app y audiencia. No sirve como Bearer.
  - `POST /auth/mfa/verify` valida TOTP o un código de recuperación y emite los tokens
    con el rol actual del grant. Si el grant fue revocado entre ambos pasos, responde
    `403`.
- Códigos incorrectos usan contadores dedicados `mfaFailedAttempts`/`mfaLockoutUntil`:
  tras `MAX_LOGIN_ATTEMPTS` fallos se bloquea el desafío durante
  `LOCKOUT_DURATION_MS` (`423 ACCOUNT_LOCKED`). Un login con contraseña correcta no
  resetea estos contadores.
- Los códigos de recuperación (10, formato `XXXXX-XXXXX`) se consumen atómicamente y no
  vuelven a funcionar. También sirven para desactivar MFA.
- `POST /auth/mfa/disable` exige contraseña y TOTP o código de recuperación; limpia todo
  el estado MFA.
- Los secretos TOTP se guardan en claro en MongoDB (riesgo aceptado y documentado) pero
  nunca se devuelven en `toJSON` ni se registran en logs.

## API

| Método | Ruta                 | Autenticación        | Respuesta                             |
| ------ | -------------------- | -------------------- | ------------------------------------- |
| `POST` | `/auth/login`        | pública              | tokens o `mfaRequired`                |
| `POST` | `/auth/mfa/verify`   | challenge en el body | `200` tokens / `400` / `401` / `423`  |
| `POST` | `/auth/mfa/enroll`   | access token         | `200` secreto / `401` / `409`         |
| `POST` | `/auth/mfa/activate` | access token         | `200` códigos / `400` / `401` / `409` |
| `POST` | `/auth/mfa/disable`  | access token         | `204` / `401` / `409`                 |

## Seguridad y despliegue

- `mfaSecret`/`mfaPendingSecret` son secretos: no se serializan ni se registran. Un dump
  de la base de datos los expondría; se acepta como riesgo de esta fase.
- Activar MFA revoca los refresh tokens previos, pero no los access tokens ya emitidos
  (siguen válidos hasta `exp`).
- Desactivar no revoca sesiones: el límite de seguridad es el alta.
- Rollback: desactivar MFA para los usuarios o revertir el cambio; los campos nuevos son
  opcionales y no requieren migración.

## Fuera de alcance

- WebAuthn/SMS, regeneración de códigos de recuperación, reset de MFA por el owner,
  dispositivos de confianza, rate limiting adicional en enroll/activate/disable y
  política MFA por aplicación.

## Verificación

- `pnpm lint`, `pnpm format:check`, `pnpm build`.
- `pnpm test:unit`: TOTP (vectores RFC), Base32, códigos de recuperación, otpauth y JWT
  de challenge.
- `pnpm test:integration`: alta/activación, verificación TOTP y recuperación, bloqueo,
  desactivación y revocación de sesiones.
- `pnpm test:e2e`: AC-1 a AC-5, challenge rechazado como Bearer y bloqueo tras fallos.

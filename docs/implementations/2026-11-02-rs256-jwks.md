# Firma RS256 y publicación de JWKS

Fecha: 2026-11-02
Issue: #39 — Firmar tokens con RS256 y publicar JWKS

## Contexto

Todos los tokens se firmaban con HS256 usando un `JWT_SECRET` compartido. Cualquier
servicio que conociera el secreto podía firmar tokens válidos, y un token emitido
para una aplicación servía también para las demás. El modelo `Application`/`Grant`
de #38 ya describía aplicaciones y permisos, pero la emisión de tokens seguía sin
audiencia.

## Decisión

- Los tokens nuevos se firman con RS256. La clave privada nunca sale del servicio y
  los consumidores verifican con la clave pública publicada en JWKS.
- Cada clave se identifica con un `kid`. Si no se configura `JWT_KEY_ID`, se usa el
  thumbprint RFC 7638 de la clave pública, que es estable entre arranques.
- La rotación se modela como una clave activa que firma y una lista de claves
  públicas retiradas que siguen resolviendo `kid` durante la ventana de migración.
  No hay tabla de claves ni rotación automática.
- Los tokens de acceso incluyen `iss`, `sub` (y el antiguo `userId`), `role`, `type`,
  `jti` y `exp`. Los tokens ligados a una aplicación añaden `aud` con la audience de
  `Application` y usan el rol del `Grant` (`viewer`/`editor`/`admin`).
- La verificación de una audiencia concreta se expone como
  `AuthenticationMiddleware.authenticateForAudience(audience)`. El
  `authenticate` antiguo rechaza cualquier token que lleve `aud` para que un token
  de aplicación no pueda usarse en las rutas globales de `/users`.
- `ApplicationTokenService` resuelve aplicación activa y grant, y emite el access
  token con audiencia. Es el punto de entrada que #40 usará desde el login; esta
  issue no añade rutas HTTP.

## Configuración

| Variable                  | Obligatoria      | Uso                                                   |
| ------------------------- | ---------------- | ----------------------------------------------------- |
| `JWT_PRIVATE_KEY`         | Sí en producción | PEM PKCS#8 de la clave activa (admite `\n` escapados) |
| `JWT_PUBLIC_KEY`          | Recomendada      | PEM SPKI de la clave activa; si falta se deriva       |
| `JWT_KEY_ID`              | No               | `kid` explícito de la clave activa                    |
| `JWT_RETIRED_PUBLIC_KEYS` | No               | JSON `[{ "kid": "...", "publicKey": "..." }]`         |
| `JWT_ISSUER`              | No               | `iss`; por defecto `auth-service`                     |
| `JWT_SECRET`              | Solo migración   | Verifica tokens HS256 antiguos sin audiencia          |

Sin `JWT_PRIVATE_KEY` el servicio no arranca salvo que se configure
`JWT_ALLOW_EPHEMERAL_KEYS=true`, pensado solo para desarrollo y tests. El modo efímero
genera un par por proceso, de modo que tokens y JWKS no coinciden entre réplicas: no
debe usarse en despliegues reales. Configurar `JWT_PUBLIC_KEY` sin
`JWT_PRIVATE_KEY` es siempre un error, para no publicar silenciosamente una clave
distinta a la esperada. Las claves RSA de menos de 2048 bits, los pares que no
coinciden y los `kid` duplicados se rechazan al construir el keyring.

## Endpoint

`GET /.well-known/jwks.json` devuelve `{ "keys": [{ kty, use, alg, kid, n, e }] }`
con `Cache-Control: public, max-age=300`. Es público, no requiere autenticación y no
incluye material privado. La caché corta permite que una rotación se observe en
minutos.

## Rotación de claves

1. Desplegar en todas las instancias la clave nueva como activa y la anterior en
   `JWT_RETIRED_PUBLIC_KEYS`.
2. Confirmar que el JWKS publica ambos `kid` y que los tokens nuevos usan el nuevo.
3. Esperar el TTL máximo de refresh token.
4. Retirar la clave antigua de `JWT_RETIRED_PUBLIC_KEYS`.

Todas las instancias deben compartir la misma configuración de claves: si no, los
tokens y el JWKS divergen entre réplicas.

## Migración desde HS256

`JWT_SECRET` se conserva solo para verificar tokens HS256 ya emitidos, únicamente
cuando no se espera una audiencia y el token no lleva `aud`. Los tokens nuevos son
siempre RS256. Pasos:

1. Desplegar esta versión con `JWT_SECRET` todavía configurado.
2. Esperar a que caduquen los access tokens y refresh tokens HS256 (máximo
   `JWT_REFRESH_EXPIRATION`).
3. Eliminar `JWT_SECRET` del entorno.

La emisión de login sigue sin audiencia hasta #40; el plan es que el refresh y el
login por aplicación se conecten a `ApplicationTokenService` en esa issue.

## Verificación

- `pnpm lint`, `pnpm format:check`, `pnpm build`.
- `pnpm test:unit`: keyring (thumbprint, rotación, validaciones), JWT (RS256,
  audiencia, firma manipulada, `kid` desconocido, compatibilidad HS256),
  middleware y controlador JWKS.
- `pnpm test:integration`: emisión de token de aplicación contra aplicación y grant
  reales, rechazo sin grant, con usuario eliminado y con aplicación inactiva.
- `pnpm test:e2e`: `/.well-known/jwks.json` público, login con access token RS256
  verificable con la clave publicada.
